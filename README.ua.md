# optiplex-fan-control

Тризонне керування вентилятором для Dell OptiPlex Micro на Linux.
Тихий idle замість дарма гучної стокової кривої, і примусовий максимум
там, де BIOS розганяється надто пізно.

[English](README.md) · українською

> Розроблено й заміряно на **OptiPlex 7080 Micro** (i5-10500T, Ubuntu 26.04,
> ядро 7.0). Інші OptiPlex із `dell_smm_hwmon` мають працювати, але пороги
> під свою машину треба перевіряти самому — див. `thermal-test.sh`.

**Ключові можливості**

- **Тихий idle.** EC має рівень ~1130 об/хв, яким BIOS ніколи не користується.
  На моєму конкретному конфізі стокова крива тримає **2000+ об/хв навіть на
  холодному CPU** — чутно навіть у тихій кімнаті; цей демон реально вмикає
  тихий рівень замість того.
- **Агресивний розгін під навантаженням** — примусовий максимум там, де
  стокова крива реагує запізно і дає процесору грітися більше, ніж треба.
- **Захист від перегріву зі звуковим сигналом.** На 95°C машина пікає й іде в
  повний продув; якщо за дві хвилини не вдається збити нижче 80°C — один довгий
  біп, і вона вимикається сама. Повертається із заклиненим (вимкненим)
  керуванням вентилятором і пікає про це — тиха відмова ніколи не лишається
  тихою.

## Встановлення

```bash
curl -fsSL https://raw.githubusercontent.com/despotix/dell-mff-fan-controller/main/get.sh | sudo bash
```

Інсталятор питає про кожен поріг, показуючи поточні значення як дефолти —
тож повторний запуск це і є спосіб переналаштувати. Git на цільовій машині
не потрібен: тарбол тягнеться через curl.

Без питань, на дефолтах (або зі збереженням наявного конфіга):

```bash
curl -fsSL https://raw.githubusercontent.com/despotix/dell-mff-fan-controller/main/get.sh | sudo bash -s -- -y
```

З клону:

```bash
sudo ./install.sh      # покроково, з поточними значеннями як дефолт
sudo ./install.sh -y   # без питань
sudo ./uninstall.sh    # прибрати, BIOS auto повертається при зупинці
```

Перевірити:

```bash
systemctl status optiplex-fan
journalctl -u optiplex-fan -f
```

## Проблема

Stock BIOS тримає вентилятор на ~1800 RPM навіть на холодному CPU (35-40°C),
а далі керує ним східчасто. Мета була — зробити idle тихішим.

Точні обороти на холостому ходу залежать від конкретної збірки (диски,
пам'ять, обдув корпусу — все зсуває базову лінію EC). На моєму конкретному
конфізі стокова крива тримає **2000+ об/хв на холодному CPU** — помітно вище
за базові ~1800 RPM вище, і чутно навіть у тихій кімнаті. Саме цей розрив між
"CPU холодний" і "вентилятор гучний" — причина існування тихого рівня
(~1130 RPM): BIOS ним ніколи не користується, хоча EC його підтримує.

## Що насправді вміє залізо

Заміряно скриптом `fan-diag.sh` (він нічого не встановлює й гарантовано
повертає BIOS auto на виході):

Прохід усього діапазону з кроком 25 при 35-40°C, по 12 секунд на значення:

| записано | readback | об/хв | рівень EC |
|---|---|---|---|
| 0, 25, 50, 75, 100, 125, 150, 175 | 128 | ~1133 | 1 |
| 200, 225, 250, 255 | 255 | ~3270 | 2 |
| `pwm1_enable=2` (BIOS auto) | `No data available` | 1803 | — |

Висновки:

- **Запис у `pwm1` працює** — але SMM-інтерфейс приймає не 0-255, а рівень
  `0..fan_max`, де тут `fan_max=2`. Драйвер конвертує через
  `DIV_ROUND_CLOSEST(pwm × fan_max, 255)`, тож межа другого рівня — **pwm 192**,
  а не 255.
- **Рівень 0 недосяжний**: запис 0 читається назад як 128, тобто рівень 1 — EC
  піднімає запит. Стану, повільнішого за 1130 об/хв, не існує.
- **Кожен запис у `pwm1` викликає короткий продув** — і це перетворює верхній
  рівень на два придатні стани. Записаний один раз, він дає сплеск ~4260 і за
  дванадцять секунд сідає на ~3250. Переписуваний щодві секунди — тримає
  4477-4773 без спаду. Зупини перезапис, і за дванадцять секунд повертається на
  ~3260. Усе це заміряно при стабільних 32-38°C, тож це не реакція EC на нагрів,
  а сам факт запису. Перезапис кожні 5 с тримає лише ~3720; кожні 10 с і рідше
  вже не відрізняється від «не чіпати».

Тож досяжні стани такі:

| стан | об/хв | як досягається |
|---|---|---|
| quiet | ~1130 | рівень 1 |
| BIOS auto | 1800 на idle, до ~2900 під навантаженням | `pwm1_enable=2` |
| boost | ~3250 | записати 255 один раз і не чіпати |
| purge | ~4600 | переписувати 255 кожні ~2 с |

**Плавна крива все одно неможлива** — це чотири дискретні точки, а не рампа —
але їх чотири, а не дві, і верхні дві коштують лише одного запису.
- Записи поза діапазоном не відхиляються, а затискаються: `1000` стає 255,
  `-1` стає 0 (і EC піднімає його до рівня 1). Понад 255 сенсу немає — рівень 2
  це стеля прошивки. `pwm1_enable` приймає лише 1 і 2; `0` і `3` відхиляються
  з `EINVAL`, тож четвертого режиму за конвенцією hwmon тут не сховано.
- Зате тихий рівень (**1130**) помітно нижчий за idle самого BIOS (**1803**).
  Саме на цьому й побудоване робоче рішення.
- Перемикання туди-назад безпечне: після `pwm1_enable=2` EC за ~10 с сам
  повертається на свої 1803 RPM (у замірах: 2531 → 2126 → 1969 → 1847 → 1812).
- Момент входу в ручний режим EC відпрацьовує сплеском на максимум
  (4373 RPM), тому демон одразу після `pwm1_enable=1` пише цільовий рівень,
  щоб сплеск тривав частку секунди.

> Попередня редакція цього README стверджувала, що записи в `pwm1` апаратно
> ігноруються, і що BIOS auto сам по собі тихий. Обидва твердження хибні —
> той тест, схоже, робився без переведення в `pwm1_enable=1`, а «вдвічі нижчі
> оберти» замірялися ще під час активного ручного override.

## Термотест: чого варта стокова крива

Два прогони по 12 потоків на цій же машині (`fan-diag.sh` для рівнів,
`stress-ng`/`openssl` для навантаження):

| прогін | фан на старті | максимум пакета |
|---|---|---|
| фан лінивo повз 1125 → 1783 | ~1780 об/хв | **91°C** |
| фан уже розкручений | ~2570 об/хв | **81°C** |

На 90°C стокова крива тримала лише 1783 об/хв із ~4800, які фан видає на
рівні 2 під навантаженням, і до 2600-2990 розганялась аж під кінець восьмої
хвилини. **BIOS віддає
десять градусів запасу тільки через те, що розганяється із запізненням.**
Це, а не саме навантаження, і є причиною 91°C.

Профіль першого прогону:

```
  сек   темп    об/хв   режим
    0    38C     1125   quiet
   36    64C     1126   quiet
   41    67C     1126   BIOS auto     ← передача на T_QUIET, як налаштовано
   56    71C     1775   BIOS auto
  161    87C     1783   BIOS auto     ← фан і досі на рівні idle
  479    91C     2951   BIOS auto     ← максимум
```

### Третій прогін: уже по тризонному демону

`stress-ng --cpu 12 --cpu-method matrixprod`, 5 хвилин, бойовий конфіг
(`T_QUIET=65`, `T_HOT=85`, `T_HOT_HYST=5`, `T_PANIC=95`):

```
  сек   темп    об/хв   зона
  222    83C     2165   BIOS      рівновага стокової кривої
  225    84C     4702   MAX       поріг перетнуто, фан вистрілив
  231    81C     4601   MAX
  235    79C     4811   MAX
  238    78C     4037   BIOS      нижче 80 — віддано BIOS-у
  250    78C     2209   BIOS
```

Максимум пакета — **84°C**, захист на 95°C і близько не підійшов. Зона
max зняла **6 градусів за 10 секунд** і відпустила через 13 с; за п'ять
хвилин навантаження — один такий цикл.

Зверни увагу, де сідає рівновага: під цим навантаженням стокова крива
тримає 83-84°C. З `T_BOOST=75` цей режим тепер потрапляє у зону boost, а
поріг purge (85°C) лишається відсічкою пікiв. Під важчим навантаженням
(перший прогін дав 91°C) зона вмикатиметься надовго.

## Робоче рішення: тризонний демон

Файли: `optiplex-fan-control.sh`, `optiplex-fan.service`, `install.sh`,
`uninstall.sh`.

| зона | умова | що робить |
|---|---|---|
| quiet | нижче `T_QUIET - T_HYST` (55°C) | ручний режим, ~1130 об/хв |
| auto | `T_QUIET` (65°C) .. `T_BOOST` | `pwm1_enable=2`, штатний BIOS |
| boost | `T_BOOST` (75°C) .. `T_PURGE` | pwm 255 записаний один раз, ~3250 об/хв |
| purge | від `T_PURGE` (85°C) | pwm 255 з перезаписом щоцикл, ~4600 об/хв |

Нижня зона прибирає дарма гучний idle (BIOS крутить 1803 там, де досить
1130). Верхня перекриває млявий розгін, задокументований вище. Середину
лишено BIOS-у: там його крива поводиться нормально.

Кожна зона відпускає нижче за точку входу, щоб фан не смикався на межі,
і в кожної свій гістерезис: `T_HYST` (10°C) для тихої, `T_HOT_HYST`
(5°C) для двох верхніх. У верхніх власна ручка навмисно — щойно фан
піднявся, він має там лишатись, поки пакет справді не охолов, а не просто
просів на градус.

Поведінка з перезаписом і є тим, що відрізняє boost від purge, тому вона
навмисна в обидва боки: у purge демон переписує `pwm1` щоцикл, бо в цьому
весь механізм, а в quiet і boost — **лише якщо** readback з'їхав із
очікуваного рівня. Зайвий запис там штовхнув би фан у той самий продув,
якого ці зони уникають.

Наслідок, про який варто знати: під тривалим навантаженням фан
циклитиметься між максимумом і BIOS-кривою. Це неминуче — проміжного
рівня в EC немає. Хочеш тихіше ціною градусів — піднімай `T_BOOST` і
`T_PURGE`; хочеш рідших перемикань — збільшуй `T_HOT_HYST`.

Усі шляхи відмови ведуть у BIOS auto: trap на `EXIT/TERM/INT/ABRT`,
нечитабельна температура, а якщо цикл зависне з фаном на ручному рівні —
`WatchdogSec=30` перезапустить сервіс, і trap відпрацює на виході.

### Захист від перегріву (`T_PANIC`) — типово вимкнений

Постачається вимкненим (`T_PANIC=0`); `install.sh` питає окремо, чи
вмикати. Вимкнути сервер — надто різка дія, щоб діставатись у спадок
разом із дефолтами.

Одне правило з дедлайном. Коли пакет доходить до `T_PANIC` (95°C) — фан уже
на максимумі з зони purge і все одно не витягує — демон:

1. **вмикає сигнал** — два коротких піки внутрішнім спікером, запис у journal,
   і тримає фан у продуві;
2. **чекає** — `PANIC_TIMEOUT` (120 с), поки пакет повернеться до
   `PANIC_RECOVER` (80°C).

Якщо повернувся — на цьому все: сигналу вистачило, звичайна логіка зон
відновлюється, робота триває. Якщо час вийшов, а пакет усе ще вище
`PANIC_RECOVER` — охолодження програло: один довгий біп і `PANIC_ACTION`.

**Типово це вимкнення, а не ребут.** Пакет, який не вдалося остудити на ходу,
не остудиться від того, що машина одразу підніметься назад у те саме
навантаження, а під час POST вентилятором взагалі ніхто не керує. Для машини,
яка мусить піднятись сама, став `PANIC_ACTION=reboot`.

У будь-якому разі демон спершу фіксує латч — пише
`/var/lib/optiplex-fan/panic`, — щоб машина, яка впала будь-де в цій
послідовності, все одно повернулась у відомий стан. Далі віддає фан BIOS-у
(зависання вимкнення не має лишити його на ручному рівні), робить `sync` і
`systemctl <дія> --force`.

**Латч — це файл, а не вимкнений unit.** На наступному старті
`optiplex-fan.service` таки запускається; він читає прапорець, не керує нічим,
лишає фан на стоковій кривій BIOS і пікає трьома довгими піками, щоб про це
сказати. Саме в цьому сенс файлу: вимкнений unit не може заявити про себе.
Розібравшись із причиною:

```bash
sudo rm /var/lib/optiplex-fan/panic
sudo systemctl restart optiplex-fan
```

Поріг обраний за вимірами: під повним навантаженням зі стоковою кривою
пакет доходив до 91°C, тож 85 спрацьовував би на кожній серйозній збірці
чи бекапі (за логом — на 136-й секунді). 95°C лишає запас над реальним
навантаженням і все одно нижче `crit=100`. Двохвилинний дедлайн — це те, що
знешкоджує сплески: короткий пік повертається під 80°C задовго до його кінця.

Врахуй, що `--force` пропускає штатний розмонтаж; `sync` перед ним
пом'якшує, але не скасовує ризик.

`T_PANIC=0` (дефолт) вимикає захист, `T_BOOST=0` і `T_PURGE=0` — відповідні
верхні зони.

### Звукова сигналізація

Усе описане вище падає безпечно — в BIOS auto, — правильно й абсолютно
мовчазно: машина, якій демон був потрібен найбільше, — це саме та, що лишається
на стоковій кривій. Тихого простою нема, boost нема, захисту нема, і ніщо про
це не каже. `optiplex-fan-alarm.sh` — це і є те несказане речення.

Два сигнали, бо означають різне:

| що чути | що це означає |
|---|---|
| два коротких піки | проблема зараз — демон не працює, або захист щойно спрацював і йде продув |
| три довгих піки | керування вентилятором **вимкнено** — захист заклинило, або демон не піднявся й лишився заклиненим |
| тиша | демон працює нормально |

Хто їх видає: демон кличе скрипт напряму (`--alert short|long`) для сигналів
захисту й для оголошення про заклинений стан, яке робить при старті. Понад те,
`optiplex-fan-alarm.service` чекає `ALARM_DELAY` секунд раз на завантаження й
пікає, якщо `optiplex-fan.service` не працює взагалі — єдиний випадок, про який
мертвий демон доповісти не може. Саме тому це окремий unit. Заклинений демон
працює, тож завантажувальна перевірка мовчить і дає йому сказати за себе, а не
повторює те саме двічі.

Сигнал програється `ALARM_REPEATS` разів — типово три — і на тому все. Він і
має читатись як помилка, а не як сповіщення: короткі різкі піки, майже на
повній амплітуді. Поки демон працює нормально, не пікає ніщо — тож пік від цієї
машини завжди означає, що щось не так.

```bash
sudo optiplex-fan-alarm.sh --test          # пікнути зараз, хай там що з демоном
sudo optiplex-fan-alarm.sh --check         # стан, латч і бекенд, без звуку
sudo optiplex-fan-alarm.sh --now           # та сама перевірка, але без затримки
sudo optiplex-fan-alarm.sh --alert long    # програти конкретний сигнал
```

**Чим воно пікає.** `ALARM_BACKEND=auto` бере `beep(1)`, якщо той встановлений,
далі — консольний дзвінок ядра: `ESC[10;<Гц>]` задає тон, `ESC[11;<мс>]` —
тривалість, `BEL` пікає, і обидва повертаються до дефолтів ядра. І те, й те —
драйвер `pcspkr`, який Ubuntu типово тримає в блеклісті; блеклист глушить лише
завантаження за аліасом, тож пікалка просить модуль по імені й отримує його.

Чого `auto` знати не може — чи веде той дріт хоч кудись. Купа машин, і 7080
Micro серед них, вантажать драйвер, показують input-пристрій «PC Speaker» — і
не мають припаяного баззера. У `/sys` про це не написано ніде. Саме для цього в
інсталяторі є питання *чути було?*: відповідаєш «ні» — і він по черзі проходить
виходи звукової карти, а той, який ти підтвердиш, іде в конфіг як
`ALARM_BACKEND=alsa` плюс `ALARM_ALSA_DEV`.

Бекенд `alsa` генерує синус сам — `awk` пише сирі 8-бітні семпли, `aplay` їх
грає, — тож тон тієї самої висоти й довжини, що й у решти бекендів, а не те, що
видасть `speaker-test`. Без прив'язки він пробує кожен залізний пристрій зі
списку `aplay -l` (а там аналоговий кодек, тобто вбудований динамік, іде поперед
HDMI) і лише потім `default`. Залізо першим тому, що на старті це працює від
root без сесії, для якої існує `default`: він або впаде, або — що гірше —
спрацює в сплячий монітор.

Якщо карта на мить зайнята — звуковий сервер, який ще не заснув, — пік не
вдається, і решта повторів це і є повторні спроби, через п'ять секунд. Якщо на
машині нема ні баззера, ні карти, пікалка пише про це в журнал і мовчить:
`--check` покаже `backend: none`, а інсталятор попередить ще до того, як ти на
неї погодишся.

`thermal-test.sh` чи `pwm-sweep.sh` із зупиненим сервісом завантажувальну
перевірку не розбудять: вона одна на завантаження, а не постійна.

## Конфігурація

Конфіг: `/etc/optiplex-fan.conf` (`T_QUIET`, `T_HYST`, `T_BOOST`, `T_PURGE`,
`T_HOT_HYST`, `QUIET_PWM`, `INTERVAL`; `T_PANIC`, `PANIC_RECOVER`,
`PANIC_TIMEOUT`, `PANIC_ACTION` для захисту від перегріву; `ALARM`,
`ALARM_DELAY`, `ALARM_REPEATS`, `ALARM_BACKEND` для сигналізації). Повний
перелік із поясненнями — у коментарях самого файлу, які пише інсталятор.
Після ручного редагування — `sudo systemctl restart optiplex-fan`.

## Мова

Скрипти за замовчуванням англійською. `FANCTL_LANG` перемикає на будь-який
файл із теки `lang/`:

```bash
FANCTL_LANG=uk sudo ./install.sh
curl -fsSL .../get.sh | sudo FANCTL_LANG=uk bash
```

Не встановлена — англійська. Значення без відповідного `lang/<значення>.sh`
дає попередження і англійську; будь-яке повідомлення, якого немає в перекладі,
лишається англійським — неповний переклад деградує, а не порожніє. Навмисно не
прив'язано до `LANG`/`LC_ALL`: українська локаль — це про дати й сортування, а
не прохання перемкнути мову інсталятора тому, хто читав англійську документацію.

Щоб додати мову, скопіюй `lang/uk.sh`, переклади праві частини і збережи всі
`%s` у тому ж порядку. Сам демон завжди пише англійською — журнал призначений
для грепу.

## BIOS-токени через `cctk` (Dell Command | Configure)

Окрема гілка розслідування: чи не можна дістати з BIOS більше рівнів, ніж
дає SMM.

### Встановлення cctk

Пакети беруться з офіційної сторінки драйверів Dell (Dell Command |
Configure для Linux, збірка під Ubuntu 18.04):

```bash
sudo apt install ./srvadmin-hapi_9.5.0_amd64.deb \
                 ./command-configure_4.10.0-595.ubuntu18_amd64.deb
```

Пакет зібраний під Ubuntu 18.04 і вимагає `libcrypto.so.1.1` /
`libssl.so.1.1` (OpenSSL 1.1) — на Ubuntu 26.04 їх уже немає в жодному
репозиторії (перевірено: security.ubuntu.com, old-releases.ubuntu.com,
archive.debian.org, snapshot.debian.org — усюди 404, пакет остаточно
прибраний після EOL). Робоче рішення — узяти бібліотеки з snap-пакета
`core18` (офіційний Canonical-снепшот рантайму Ubuntu 18.04 Bionic, який
використовують інші snap як базу):

```bash
sudo snap install core18
sudo cp /snap/core18/current/usr/lib/x86_64-linux-gnu/libssl.so.1.1    /opt/dell/dcc/
sudo cp /snap/core18/current/usr/lib/x86_64-linux-gnu/libcrypto.so.1.1 /opt/dell/dcc/
sudo ldconfig
sudo /opt/dell/dcc/cctk --Version   # перевірка, що працює
```

`cctk` (навіть у режимі читання) завжди вимагає root — без `sudo` видає
`'admin/root' privileges required to execute this application.`

### Що реально доступно на цьому BIOS

У самому бінарнику `cctk` зашиті рядки для набагато багатшого набору
fan-токенів — `FanSpdAutoLvlonCpuZone`, `FanSpdAutoLvlonPcieZone`,
`FanSpdCpuMemZone`, `FanSpdStorageZone` та інші (мінімальний рівень
швидкості по тепловим зонах). Але `cctk --help`, запущений на цій машині,
показує тільки той набір токенів, який реально є в SMBIOS-таблиці **цього**
BIOS — і з усього fan/thermal там лишився один:

```
FanCtrlOvrd — Controls the speed of the fan.
  Enabled  - The system fan is set to full speed.
  Disabled - The system run time sets the fan speed to optimal.
```

Тобто через BIOS-канал додаткових рівнів не дістати — це вимикач «завжди
повна швидкість», не крива. Поточне значення на машині: `Disabled`.

### Якщо фан колись застрягне на максимумі

`FanCtrlOvrd=Enabled` прибиває вентилятор до повної швидкості на рівні
прошивки, нижче ОС — жоден демон цього не перекриє, і ребут не допоможе.
Це не дефолт, але оновлення BIOS, скид CMOS чи випадкова команда можуть
його там лишити. Лікується однією командою:

```bash
sudo /opt/dell/dcc/cctk --FanCtrlOvrd=Disabled
```

Раніше тут лежала тека `cctk-baseline/` — systemd oneshot, який робив те
саме при кожному завантаженні. Прибрано: подія разова й одразу помітна
на слух, а сервіс усе одно зламався б разом із cctk на апгрейді ОС.

## Діагностика

```bash
sudo ./fan-diag.sh
```

Показує стан `FanCtrlOvrd` і прогонює фан через усі режими з замірами RPM.
Нічого не встановлює; на виході — включно з Ctrl+C — повертає `pwm1_enable=2`.

Підібрати пороги під свою машину:

```bash
sudo ./thermal-test.sh          # 300с навантаження за замовчуванням
sudo ./thermal-test.sh 600      # довше
```

На моделі, відмінній від 7080 Micro, почни з `sudo ./pwm-sweep.sh` — межі
рівнів вище заміряні, а не взяті з документації, і в тебе можуть бути інші.

Вантажить усі ядра (`stress-ng`, а якщо його немає — `openssl`) і показує,
де сідає температура. Сам знімає навантаження на 93°C, щоб живий `T_PANIC`
не ребутнув машину посеред тесту. Запусти раз із зупиненим сервісом і раз
із запущеним — побачиш різницю між стоковою кривою і демоном.
